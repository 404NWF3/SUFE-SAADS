  三、AI/LLM 编排框架

  本系统的核心智能组件基于以下开源平台构建：

  （1）LangChain（版本 1.2.8，官网：https://www.langchain.com）

  LangChain 为大语言模型应用提供统一抽象层，屏蔽不同 LLM
  供应商（Qwen、GLM、OpenAI 等）的接口差异。本系统调用 langchain-core 
  1.2.9、langchain-openai 1.1.7（OpenAI 兼容接口适配器）、langchain-google-genai
   4.2.0（Google Gemini 接口）及 langchain-qdrant 
  0.2.0（向量库集成）等子包，实现：提示词管理、LLM 链式调用、工具调用（Tool
  Use）以及向量检索增强生成（RAG）。

  （2）LangGraph（版本 1.0.7，官网：https://langchain-ai.github.io/langgraph）

  LangGraph 是基于有向图（DAG）的多智能体编排框架。本系统的 WP1-1
  攻击情报处理模块（backend/agents/intel_agents/orchestrator/graph.py）以
  LangGraph 为运行时，实现以下功能：
  - 定义多智能体状态机（WP11GraphState），管理情报采集、去重、标准化、BOM
  解析等阶段的状态转移；
  - 利用 Send API 实现并发扇出（fan-out），同时驱动多个情报条目的处理；
  - 借助 langgraph-checkpoint 4.0.0
  提供可持久化的图状态检查点，支持长时任务断点恢复。

  （3）LangSmith（版本 0.6.9，官网：https://smith.langchain.com）

  用于 LLM 调用的全链路追踪与可观测性，记录每次模型调用的输入/输出、延迟与 Token
   消耗，辅助调试与性能优化。

  模型池按任务类型（planning、reflection、standardization、bom_resolution、dedup
  _merge 等）配置路由预设（wp11_llm_route_presets.json），按成本/可靠性等级分为
  三档（cheap_fast、balanced、fallback），每档最大并发数为 16，冷却时间 20 秒。

  模型调用关键实现调用了 OpenAI Python SDK（版本
  2.17.0，官网：https://github.com/openai/openai-python）作为底层客户端，向所有
  OpenAI 兼容端点发起请求。结构化输出（Structured Output）通过 function_calling
  方式实现，针对 Qwen3 系列模型在结构化输出时自动关闭思维链以保证 JSON
  格式正确性。

  五、向量数据库与嵌入模型

  （1）Qdrant（版本 1.13.0，官网：https://qdrant.tech）

  Qdrant 是开源高性能向量数据库，本系统用于：攻击情报语义去重（Dedup）的向量签名
  存储与相似度检索，以及语义搜索增强。集合名称为 saads_attacks，支持本地模式（.r
  untime/wp11/vector_memory）与远程服务两种部署方式。

  （2）嵌入模型

  - 默认：OpenAI text-embedding-3-small（1536 维），通过 DashScope
  兼容接口调用；
  - 可选本地模型：sentence-transformers（版本
  ≥3.0.0，官网：https://sbert.net），加载 all-MiniLM-L6-v2（384
  维），用于无网络环境部署；
  - 去重签名维度：32 维（降维压缩，用于快速匹配）。

  一、系统部署架构

  本系统采用分布式微服务架构，分为前端展示层、后端服务层、数据持久层三个逻辑层次
  ，各层独立部署，通过标准化接口通信。整体为客户端-服务器（C/S）+ 
  浏览器-服务器（B/S）混合架构，用户通过浏览器访问前端界面，前端通过
  HTTP/WebSocket 与后端 API 服务交互。

  系统组件连接关系如下：

  3.1 系统结构设计

  3.1.1 技术架构

  一、整体架构模式

  本系统采用 B/S（Browser/Server）架构作为用户交互层，以 分布式微服务
  作为后端服务层，整体构成"前后端分离 + 多智能体协同"的复合架构。选择 B/S
  架构的原因在于：系统面向安全运营人员的日常监控与分析场景，用户无需安装任何本地
  客户端即可通过浏览器访问实时威胁态势看板；而后端服务层的无状态设计使其可在需要
  时横向扩展，满足大批量情报处理的并发需求。

  系统不涉及移动端平台。

  ---
  二、技术选型与理由

  （1）后端：FastAPI + Uvicorn（异步 ASGI 架构）

  后端采用 FastAPI 0.128.2（Python，官网：https://fastapi.tiangolo.com）作为 Web
   框架，运行于 Uvicorn 0.40.0 ASGI 服务器之上。选择理由：

  - FastAPI 原生基于 Python asyncio，与系统中大量并发 LLM API
  调用、异步数据库操作的需求完全契合，避免线程切换开销；
  - FastAPI 内置 OpenAPI 文档自动生成（/docs、/redoc），便于前后端接口联调；
  - 支持原生 SSE（Server-Sent Events） 流式推送，满足前端实时监控 LangGraph
  节点执行日志的需求；
  - Pydantic v2
  深度集成，所有请求/响应数据模型在边界处自动验证，从根本上减少注入类漏洞风险。

  （2）多智能体编排：LangGraph（状态机图）

  系统的核心处理逻辑由 LangGraph 1.0.7（官网：https://langchain-ai.github.io/lan
  ggraph）驱动，以有向图（DAG）描述多智能体协作流程。选择理由：

  - 相比线性 Chain 模式，LangGraph
  将工作流建模为显式状态机，每个节点的输入/输出均通过
  WP11GraphState（TypedDict）强类型约束，状态转移可被审计和持久化；
  - 内置检查点（Checkpoint）机制，支持长时任务的断点恢复（从任意节点续跑），显著
  提升对 LLM 调用超时、网络抖动等故障的容错能力；
  - Send API 支持并发扇出（fan-out），WP1-1 的 5
  类情报源采集节点可并行驱动，无需额外线程管理；
  - 条件路由（conditional routing）使系统能根据采集质量评估结果动态决定是否触发
  反思循环或覆盖度补充循环，实现自适应的情报采集策略。

  （3）大语言模型：OpenAI 兼容接口 + 多模型路由

  系统通过 OpenAI Python SDK 2.17.0 统一接入多家国内 LLM 服务商（通义 Qwen、智谱
   GLM、MiniMax、DeepSeek），形成多模型池。选择 OpenAI
  兼容接口的原因在于：国内主流大模型服务商均已实现该接口标准，无需针对各家分别维
  护调用逻辑，且可通过统一的 llm_client_factory.py 进行成本分级路由（cheap_fast
  / balanced / fallback）和故障自动切换。

  （4）向量数据库：Qdrant

  语义去重与情报检索采用 Qdrant 
  1.13.0（官网：https://qdrant.tech）向量数据库。选择理由：Qdrant
  支持高维向量的毫秒级近邻检索，提供 Python 原生客户端与 LangChain
  集成，且支持本地文件模式（开发）和独立服务模式（生产）的无缝切换，符合本系统开
  发/生产环境兼顾的部署需求。

  （5）关系数据库：PostgreSQL + SQLAlchemy（异步 ORM）

  攻击情报条目、组件映射、BOM 解析队列、审计日志等结构化数据持久化到
  PostgreSQL（生产）或 SQLite（开发），通过 SQLAlchemy 
  2.0（官网：https://www.sqlalchemy.org）统一 ORM 层访问。选择 SQLAlchemy 2.0
  的原因在于其原生异步引擎（AsyncSession）与 FastAPI / asyncio
  无缝对接，连接池管理由 psycopg3 驱动，支持最大 10 连接并发。

  （6）前端：Next.js 16 + React 19

  前端采用 Next.js 16.1.7 元框架（官网：https://nextjs.org）和 React 19.2.3
  构建单页应用（SPA）。选择理由：Next.js
  的服务端渲染（SSR）能力使首屏数据在服务端预取，减少前端到后端的额外请求；SWR（
  stale-while-revalidate）数据请求策略保证看板数据的自动轮询刷新；react-window
  虚拟滚动组件解决大量情报条目列表的渲染性能问题。

  Routers），形成清晰的分层架构。

  三、主要模块说明

  【WP1-1 情报采集与处理模块】

  WP1-1 是系统的核心流水线，负责从多源网络（漏洞数据库、代码平台、学术论文、社区
  论坛、安全公告）自动采集 AI 系统攻击情报，并经过标准化、语义去重、BOM
  组件解析、STIX 格式化等阶段，形成高质量结构化攻击知识库。由

  二、语义去重与合并算法（Semantic Dedup & Merge）

  去重模块（backend/agents/intel_agents/tools/dedup_tools.py）采用六层相似度计算
  流水线，将计算成本从低到高排布，在精准度与效率之间取得平衡：

  ┌─────────────────────────────────────────────────────────────────┐
  │              语义去重算法流程                                    │
  └─────────────────────────────────────────────────────────────────┘

  输入：新标准化攻击条目（candidate）+ 历史稳定攻击池（candidate_pool）

  第1层：内容哈希（O(1) 精确匹配）
    content_hash = SHA256(
        canonical_name + summary + description +
        sorted(taxonomy_codes) + sorted(component_names)
    )
    → 若 hash 命中 → 直接判定 merge，跳过后续层

  第2层：SimHash（汉明距离，局部敏感哈希）
    tokens = tokenize(text)  # 最小长度2字符
    for bit in 0..63:
        weight[bit] = Σ(count[token] × bit[hash(token)])
    simhash_signature = bitmask(weight > 0)
    simhash_sim = 1.0 - hamming_distance(sig1, sig2) / 64

    → 若 simhash_sim ≥ 0.95 且 (taxonomy_overlap ≥ 0.5 或 bom_overlap ≥ 0.5)
      → 判定 merge

  第3层：MinHash（Jaccard 估计，16个哈希函数）
    for seed in range(16):
        minhash[seed] = min(hash(seed, token) for token in tokens)
    minhash_sim = |{i: mh1[i] == mh2[i]}| / 16

  第4层：余弦嵌入（降维词频向量，32维）
    for token in tokens:
        vec[hash(token) % 32] += count[token]
    cosine_sim = dot(v1, v2) / (‖v1‖ × ‖v2‖)

  第5层：分类法重叠（Jaccard on OWASP/MITRE codes）
    taxonomy_overlap = |codes1 ∩ codes2| / |codes1 ∪ codes2|

  第6层：BOM 重叠（组件提及 Jaccard）
    bom_overlap = |mentions1 ∩ mentions2| / |mentions1 ∪ mentions2|

  Rerank 综合得分：
    rerank = 0.25 × name_sim + 0.20 × family_match + 0.55 × text_sim

  ┌─────────────────────────────────────────────────────────┐
  │                    决策逻辑                              │
  │                                                         │
  │  哈希命中?         ──YES──▶ merge（直接合并）            │
  │      │NO                                                │
  │  simhash ≥ 0.95   ──YES──▶ merge                       │
  │  且分类/BOM重叠?                                        │
  │      │NO                                                │
  │  minhash ≥ 0.80   ──YES──▶ review_queue（LLM二次裁决） │
  │  且cosine ≥ 0.75  →LLM置信度 ≥ 0.85 且无BOM变化→merge  │
  │  且rerank ≥ 0.70?           └─否─▶ keep_separate       │
  │      │NO                                                │
  │  keep_separate（保留为独立条目）                        │
  └─────────────────────────────────────────────────────────┘

  输出：
    merge → 两条目合并为一个 stable_attack_record
    keep_separate → 作为新条目加入攻击池
    review_queue → 进入人工/LLM二次裁决队列

  性能优化技巧：
  - 先执行 O(1) 哈希精确匹配，命中则直接合并，无需进入后续计算；
  - SimHash 和 MinHash 使用固定长度签名，向量化比较效率高；
  - 仅在 SimHash/MinHash 初步判断"疑似重复"后，才调用 LLM
  进行高成本语义裁决，大幅减少 LLM 调用次数；
  - 嵌入向量降维至 32 维（而非 1536 维），显著降低存储和比较开销。

  三、BOM 组件解析算法（三阶段渐进式解析）

  BOM 解析模块（backend/db/services/bom_resolution_service.py）将攻击情报中的非
  结构化组件提及（如"PyTorch 2.0"、"LangChain"）映射到标准化的 AI
  组件注册表，采用三阶段渐进式策略，从精确到模糊依次尝试：

  输入：mentioned_name, mentioned_vendor, mentioned_version

  ┌──────────────────────────────────────────────────────────────┐
  │               BOM 组件解析三阶段流程                         │
  └──────────────────────────────────────────────────────────────┘

  阶段1：精确名称匹配（confidence = 1.0）
    ┌────────────────────────────────────────┐
    │ SELECT * FROM ai_component             │
    │ WHERE component_name = mentioned_name  │
    └────────────────────────────────────────┘
          │ 命中 → resolved，match_mode = "exact"，返回
          │ 未命中 ↓

  阶段2：别名规范化匹配（confidence = 0.9）
    alias = normalize_component_alias(mentioned_name, mentioned_vendor)
    ┌────────────────────────────────────────────┐
    │ SELECT * FROM ai_component_alias           │
    │ WHERE normalized_alias = alias             │
    └────────────────────────────────────────────┘
          │ 命中 → resolved，match_mode = "vendor_fallback"，返回
          │ 未命中 ↓

  阶段3：模糊相似度搜索（similarity ∈ [0.7, 1.0)）
    candidates = trigram_search(alias, limit=5)

    top = candidates[0]
    second = candidates[1] if exists else None

    ┌─────────────────────────────────────────────────────┐
    │              歧义判断逻辑                            │
    │  top.similarity ≥ min_similarity (0.75)             │
    │  AND (second 不存在 OR                              │
    │       top.similarity - second.similarity ≥ 0.05)   │
    │                                                     │
    │  满足 → resolved，match_mode = "range"              │
    │         confidence = top.similarity                 │
    │  不满足 → queued（进入人工审核队列）                  │
    │           match_mode = "ambiguous"                  │
    └─────────────────────────────────────────────────────┘

  阶段4（队列处理）：LLM/人工二次审核
    BomResolutionQueueItem 持久化到 bom_resolution_queue 表
    review_ai_bom_resolution 节点调用 LLM 对歧义条目裁决
    裁决后更新 AttackComponentImpact（confidence, match_mode）

  输出：BomResolutionResult {
      status: "resolved" | "queued",
      component_id: UUID | None,
      similarity: float,
      match_mode: "exact" | "vendor_fallback" | "range" | "ambiguous"
  }

  四、LLM 模型池路由算法（成本感知故障转移）

  模型池工厂（backend/agents/intel_agents/tools/llm_client_factory.py）实现了基
  于任务类型的成本分级路由，并内置故障转移链：

  输入：task_type（如 "dedup_merge"），route_preset（如 "default"）

  ┌────────────────────────────────────────────────────────┐
  │              LLM 路由与故障转移算法                     │
  └────────────────────────────────────────────────────────┘

  Step1：查询路由预设表
    profile_chain = route_presets[route_preset][task_type]
    # 例：["balanced", "cheap_fast", "fallback"]

  Step2：遍历候选 Profile，带冷却检测
    for profile_name in profile_chain:
        profile = profiles[profile_name]

        if profile.cooldown_until > now():
            continue  # 冷却中，跳过

        if profile.active_connections >= profile.max_concurrency:
            continue  # 达到并发上限，跳过

        → 尝试调用该 Profile 的 LLM 端点

  Step3：LLM 调用（带超时）
    try:
        response = openai_client.chat.complete(
            model=profile.model,
            messages=messages,
            timeout=30s
        )
        → 成功：重置该 profile 的错误计数，返回 response

    except (RateLimitError, TimeoutError, ServerError):
        profile.cooldown_until = now() + cooldown_seconds(20s)
        continue  # 尝试链中下一个 Profile

  Step4：所有 Profile 耗尽
    raise LlmInvocationError(
        retry_after_seconds=min_cooldown_remaining
    )
    → 触发节点重试机制（最多2次），记录 resume_hint 用于断点续跑

  冷却时间：20秒（可配置）
  最大并发：每 Profile 16 路（可配置）

  四、模块间接口：WP1-1 → WP1-2 共享数据库读模型

  WP1-1 与 WP1-2 之间不直接调用函数，而是通过数据库只读视图（Read Model）
  进行异步解耦。WP1-1 将处理后的稳定攻击条目写入 wp12_attack_feed 视图，WP1-2
  通过 Wp12FeedService 查询该视图获取数据。

  Wp12AttackFeedRow（视图行结构）：

  字段名                       类型            说明
  attack_id                   UUID            攻击条目唯一标识
  attack_code                 str             标准化攻击代码（如
  LLM01-2024-0042）
  canonical_name              str             规范化攻击名称
  attack_family               str             攻击类型（如 prompt_injection）
  severity_level              str
  严重级别（info/low/medium/high/critical）
  entry_status                str             条目状态（active/archived）
  summary                     str             摘要文本
  last_seen_at                datetime?       最近出现时间
  primary_cvss_version        str?            CVSS 版本（如 3.1）
  primary_cvss_base_score     Decimal?        CVSS 基础分（0.0-10.0）
  primary_cvss_vector         str?            CVSS 向量字符串
  primary_cvss_severity_label str?            CVSS 严重性标签
  taxonomy_type               str?            分类法类型（owasp/mitre）
  taxonomy_code               str?            分类法代码（如 OWASP-LLM-01）
  taxonomy_name               str?            分类法名称
  component_id                UUID?           关联 AI 组件 ID
  component_name              str?            组件名称（如 LangChain）
  version_constraint_raw      str?            版本约束原文
  normalized_constraint       str?            标准化版本约束（如
  >=0.1.0,<1.0.0）
  component_impact_scope      str?            组件影响范围
  asset_id                    UUID?           测试资产 ID
  asset_type                  str?            资产类型（如 exploit_script）
  asset_name                  str?            资产名称
  artifact_uri                str?            制品文件路径
  qa_status                   str?            QA 状态（pending/validated）

  复制配置模板并编辑：

  打开 .env，按以下优先级填写配置：

  （1）必填：LLM 服务配置（三选一）

  # 通义 Qwen（推荐，国内访问稳定）
  GLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
  GLM_API_KEY_1=sk-your-dashscope-api-key
  GLM_MODEL=qwen-plus           # balanced 档使用
  GLM_FAST_MODEL=qwen-turbo     # cheap_fast 档使用
  GLM_CHEAP_FAST_MODEL=qwen-turbo  # fallback 档使用

  或使用智谱 GLM：

  GLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4
  GLM_API_KEY_1=your-glm-api-key
  GLM_MODEL=glm-4
  GLM_FAST_MODEL=glm-4-flash
  GLM_CHEAP_FAST_MODEL=glm-4-flash

  或使用 OpenAI 兼容接口（DeepSeek、OpenRouter 等）：

  OPENAI_API_KEY=sk-your-api-key
  # OPENAI_BASE_URL=https://api.deepseek.com/v1  # 如使用非官方 OpenAI

  （2）推荐填写：威胁情报 API 密钥（不填也能运行，但采集能力受限）

  NVD_API_KEY=your-nvd-key         # 不填则每 30 秒限 5 次请求
  GITHUB_TOKEN=ghp_your-token      # 不填则每小时限 60 次请求

  开发环境默认使用 SQLite，无需任何额外设置。如需接入 PostgreSQL：

  POSTGRES_DSN=postgresql://postgres:postgres@localhost:5432/saads
  POSTGRES_SCHEMA=wp11

  （4）向量数据库（默认使用本地嵌入模式，无需额外配置）

  Qdrant 默认以嵌入模式运行，数据存储在
  .runtime/wp11/vector_memory，无需独立部署。如需接入独立 Qdrant 服务：

  七、功能使用说明

  7.1 WP1-1：威胁情报采集（通过看板）

  1. 浏览器打开 http://localhost:3000/dashboard/wp11
  2. 在页面顶部选择运行模式：
    - bootstrap：首次全量采集，从所有来源拉取历史数据
    - incremental：增量采集，仅拉取最近更新
    - gap_fill：补充覆盖度不足的类别
  3. 点击「开始运行」，右侧日志窗口实时显示各节点执行进度
  4. 运行完成后，指标面板更新攻击知识库规模、覆盖率等统计信息
  5. 告警面板显示新发现的安全告警（覆盖度缺口、弱信号等）

  八、生产环境部署（Windows Server + Nginx）

  8.1 安装运行时

  在服务器上依次安装：
  - Python 3.11+（安装时勾选"Add to PATH"）
  - Node.js 20 LTS
  - Git
  - Nginx for Windows（解压到 C:\nginx）
  - NSSM（可选，用于将服务注册为 Windows 开机自启）

  8.2 部署代码

  git clone <仓库地址> C:\saads
  cd C:\saads
  pip install -r requirements.txt

  cd frontend
  npm install
  npm run build    # 生产构建，输出到 frontend/.next/
  cd ..

  8.3 配置 .env

  在 .env 中新增或修改：

  # 将服务器实际 IP 或域名填入
  CORS_ORIGINS=http://localhost:3000,http://127.0.0.1:3000,http://<服务器IP>

  8.4 配置 Nginx

  编辑 C:\nginx\conf\nginx.conf：

  worker_processes 1;
  events { worker_connections 1024; }

  http {
      include       mime.types;
      default_type  application/octet-stream;

      server {
          listen 80;
          server_name <服务器IP或域名>;

          # 前端静态资源缓存
          location /_next/static/ {
              alias C:/saads/frontend/.next/static/;
              expires 1y;
              add_header Cache-Control "public, immutable";
          }

          # FastAPI 后端（SSE 流必须关闭缓冲）
          location /api/ {
              proxy_pass http://127.0.0.1:8000;
              proxy_buffering off;
              proxy_set_header X-Accel-Buffering no;
              proxy_read_timeout 3600s;
              proxy_send_timeout 3600s;
              proxy_http_version 1.1;
              proxy_set_header Host $host;
              proxy_set_header X-Real-IP $remote_addr;
          }

          # Next.js 前端
          location / {
              proxy_pass http://127.0.0.1:3000;
              proxy_http_version 1.1;
              proxy_set_header Upgrade $http_upgrade;
              proxy_set_header Connection "upgrade";
              proxy_set_header Host $host;
          }
      }
  }

  启动 Nginx：

  C:\nginx\nginx.exe
  # 修改配置后重载（无需重启）：
  C:\nginx\nginx.exe -s reload

  8.5 启动服务

  方式 A（临时测试）：

  # 窗口1：后端
  cd C:\saads
  python serve.py --host 127.0.0.1 --port 8000 --no-reload

  # 窗口2：前端
  cd C:\saads\frontend
  npm run start

  方式 B（推荐：NSSM 注册为 Windows 服务，开机自启）：

  # 注册后端服务
  nssm install saads-backend python "C:\saads\serve.py --host 127.0.0.1 --port 
  8000 --no-reload"
  nssm set saads-backend AppDirectory "C:\saads"
  nssm start saads-backend

  # 注册前端服务
  nssm install saads-frontend "node_modules\.bin\next" start
  nssm set saads-frontend AppDirectory "C:\saads\frontend"
  nssm start saads-frontend

  8.6 防火墙配置

  # 开放 HTTP 端口（端口 3000 和 8000 无需对外开放，由 Nginx 内部转发）
  netsh advfirewall firewall add rule name="HTTP" dir=in action=allow
  protocol=TCP localport=80
  netsh advfirewall firewall add rule name="HTTPS" dir=in action=allow
  protocol=TCP localport=443

  十、常见问题

  Q：启动后端报 ModuleNotFoundError

  检查虚拟环境是否已激活，以及 pip install -r requirements.txt 是否完整执行。

  Q：前端请求 /api/* 返回 404

  开发模式下，前端通过 next.config.ts 中的 rewrite 规则将 /api/* 转发到
  localhost:8000，确认后端已启动。

  Q：生产环境前端无法访问后端，控制台报 CORS 错误

  在服务器 .env 中将 CORS_ORIGINS 设置为包含服务器 IP 的列表，并重启后端服务。

  Q：SSE 日志在生产环境不实时，有明显延迟

  Nginx 配置中确认 proxy_buffering off 已生效。未关闭缓冲时 Nginx 会将 SSE
  事件积累后批量发送，导致日志出现"卡顿"再"刷屏"的现象。

  Q：LLM 调用失败，报 LlmInvocationError

  检查 .env 中对应的 API Key 和 Base URL
  是否填写正确；检查网络是否能访问对应服务商的接口地址。系统会自动按
  wp11_llm_route_presets.json 中配置的顺序尝试切换模型，所有 Profile
  均失败后才会抛出异常。

  Q：想关闭 LLM 调用，仅用规则跑通流程

  在 .env 或运行时参数中将各策略设置为 rules_only，或使用命令行场景 --scenario 
  normal 的 stub 模式（默认不调用真实 LLM）。
